# 0.13.0 两级身份：fp 快速识别 + SHA-256 静默收敛（方案一+方案二）

## 先回答三个设计问题

**Q1：SHA-256 计算期间 APP 终止，音乐还能被识别吗？重启后会自动续算吗？**
能识别，完全不受影响。因为识别决策（查重/认领/合并）全部走 **fp（导入时毫秒级落库）**，SHA-256 只是后台的"权威确认"，缺它只意味着"待确认"而非"失效"。重启**自动续算**：收敛任务按 `hash=''` 状态查询待办、逐文件提交、幂等可断点续传——这正是 0.12.0 backfill 的既有机制（模拟器已实证：首轮处理 1 个被扫描打断，二次启动自动续算剩余 10 个）。

**Q2：fp 能保证唯一性吗？**
xxHash3-128：10 万文件库的随机碰撞概率 ~10⁻²⁹；结构性碰撞（不同文件采样区恰同）由**头/中/尾三窗采样 + 体积混入哈希输入**压制；小于 768KB 的文件直接**退化为全文件指纹**（更强）；SHA-256 收敛后还有**碰撞审计兜底**——真碰撞（概率趋零）被检测到后自动把这两行的 fp 升级为全文件 xxh3 消歧，自愈并留日志。结论：操作层面等同唯一，数学上有 256 位权威兜底。

**Q3：fp 做主识别、SHA-256 做静默查重？**
正是本方案架构。**fp = 操作身份**（导入查重/移动认领/退役合并/查重页/备份重挂，全部实时可用）；**hash = 权威确认**（后台静默收敛、碰撞审计、完整性校验储备）。两者各司其职，SHA-256 缺失期间全功能正常。

## 身份模型

| 层 | 字段 | 算法 | 落库时机 | 职责 |
|---|---|---|---|---|
| 操作身份 | `fp`（32位hex） | xxHash3-128(头256KB⊕中256KB⊕尾256KB⊕size)，<768KB 全文件 | 导入时同步（毫秒级） | 查重/认领/合并/查重页/备份重挂的全部决策 |
| 权威确认 | `hash`（64位hex） | SHA-256 全文件 | 后台收敛（可中断续算） | fp 碰撞审计、完整性储备 |
| 音频身份 | `pcm_md5` | FLAC STREAMINFO 自带 PCM MD5（零额外 I/O） | 导入时同步（FLAC） | **仅认领**：FLAC 改标签后移动的文件可被认领（tag 免疫） |

决策顺序：`(fp, cueStartMs)` 命中（旧文件在→跳过/失联→认领）→ fp 未中且 FLAC 且 `pcm_md5` 命中且旧文件失联→认领 → 入库。pcm_md5 不做查重跳过（同音频不同编码是合法多版本）。

## 改动清单

### 1. Native
- **vendored xxhash**：`entry/src/main/cpp/third_party/` 新增 `xxhash.h + xxhash.c`（Cyan4973/xxHash v0.8.x，BSD-2，与 dr_flac.h 同模式；CMakeLists.txt:9 源清单加 `third_party/xxhash.c`，cpp 根已在 include path）。
- **`timbrava_napi.cpp`** 新增 `fingerprintFd(fd, full) → Promise<string>`（照抄 hashFd 的异步工作模式）：full=false 读 3×256KB 窗（头/中点±128KB/尾；≤768KB 整文件），输入 = size(8字节LE)+三窗 → XXH3_128 → 32位hex；full=true 整文件 xxh3（碰撞消歧用）。fd 契约同 hashFd。

### 2. Db（`data/Db.ets`）
- `migrateSongsFp()`（marker `dbSongsFp1`）：ALTER 加 `fp TEXT NOT NULL DEFAULT ''`、`pcm_md5 TEXT NOT NULL DEFAULT ''` + `idx_songs_fp`/`idx_songs_pcm_md5`——**索引全部放本方法内**（0.12.0 踩过的时序坑：SQL_CREATE 建索引会因列未挂而断 init）。
- `SONG_COLS`/`upsertSong`/`Model.ts`（Song.fp/pcmMd5 + fromJson）同步加字段。
- 新查询：`getPathsNeedingFp`/`getPathsNeedingPcmMd5(flac)`/`getPathsNeedingHash`（均 `SELECT DISTINCT path WHERE xx=''`）；`updateSongsFpByPath`/`updateSongsPcmMd5ByPath`。
- `retireSongsByPaths` 幸存者检索：fp 优先、hash 兜底（兼容 fp 未回填的 0.12.0 行）。

### 3. ScanService（`data/ScanService.ets`）
- `parseAndStore`：meta.ok 后 `fp = await fingerprintFd(fd, false)`；三分支键 hash→fp；**原位更新分支 bucket 置 `hash:''`**（内容已变，触发重收敛）；FLAC 记 `meta.pcmMd5`；fp 未中时按 pcm_md5 认领兜底。
- `parseCueFile`：音频 fp 求值一次全轨共用（优先复用同 path 未变行的 fp），分轨键 (fp, cueStartMs)。
- `backfillHashes` → **`convergeIdentities()`** 三段串行（沿用扫描让路-等待续跑模式）：
  - Stage A（秒级）：fp='' 回填 + FLAC pcm_md5='' 回填（头解析 ~KB 级）——**全库 fp 覆盖先于 hash**；
  - Stage B（后台）：hash='' 逐文件 SHA-256；
  - Stage C：fp 碰撞审计 `GROUP BY fp HAVING COUNT(*)>1 AND COUNT(DISTINCT hash)>1` → 命中行 `fingerprintFd(fd, true)` 重算消歧 + 日志。
- PlayerController.init 调用点改名（PlayerController.ets:~935 附近，fire-and-forget 不变）。

### 4. MetaParse（`data/tag/MetaParse.ts`）
- `parseFlac` L277-284：守卫收紧 `si.length >= 34`，`meta.pcmMd5 = hex(si.subarray(18, 34))`——**字节已在现有 clampRead(34) 缓冲区内，纯提取**。`SongMeta`（L7-29）加 `pcmMd5: string = ''`。Ogg 内嵌 FLAC 路径维持跳过（L432 现状）。

### 5. BackupService + Duplicates 页
- 导出：`fpByPath`（全量）+ `hashByPath`（非空，兼容保留）；`resolveSong` 顺序 path → fp → hash（旧备份文件不含 fpByPath 自动回退 hash，兼容）。
- `Duplicates.ets`：精确分组键 (hash, cueStart) → **(fp, cueStart)**（fp 收敛快，升级后秒级全覆盖）；启发式兜底 hash→fp=''；`dup_note` 文案同步（base+en_US）。

## 已知代价（如实声明）
- 单文件生命周期总 I/O 略增（768KB 前台 + 全量后台 vs 0.12.0 全量一次），换前台零等待 + 收敛可断点续传。
- 升级后 Stage A 完成前的几秒窗口内导入可能漏查重（fp 未覆盖的旧行）——查重页兜底，仅升级首启存在。
